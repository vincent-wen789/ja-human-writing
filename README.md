# ja-human-writing

書き手の判断と語り口を活かして日本語を書く・直すための Claude Code スキル。

v0.1.1 · 2026-09

## すでに自然な文は、そのまま残す

成稿の軽い改稿では、事実や語気を保って重複などを整理する。例えば、次の説明用の文なら：

```text
今回の変更で、検索時間が短くなる可能性があります。
つまり、検索にかかる時間が短くなる可能性があるということです。
```

同じことを言い直している後半を省ける。

```text
今回の変更で、検索時間が短くなる可能性があります。
```

「可能性があります」は残す。断定を強めたり、実測していない秒数を加えたりしない。文長をばらつかせるための書き換えもしない。

## 書くときと、直すときの役割

- **新しく書く**：素材の出どころと、書き手が何を判断しているかを整理する。長文では素材5件を点検の目安にするが、件数を満たすために話を広げない。一つの十分な経験や事例でもよい。
- **成稿を直す**：構成、事実、引用、否定、条件、確信の度合いを保つ。問題のない文や作者の癖は残す。全面改稿は依頼されたときに行う。
- **指摘を判断する**：任意の [natural-japanese](https://github.com/coji/natural-japanese) が出す finding は確認の手掛かり。実際の読みにくさを説明できる箇所だけ直す。

本体は指示と手順であり、独自のAI検出プログラムは含まない。語彙・構造の候補は [stop-ai-slop-jp](https://github.com/iKora128/stop-ai-slop-jp) と [slop-nuki](https://github.com/chezou/slop-nuki) などを参考にしているが、禁止語として一律には削らない。

## v0.1.1 で見直したこと

- 極長文・極短文、一人称、体言止めを人間らしさのために強制しない。
- 三つの理由、複数の不確実な条件、実際の「AではなくB」を回数だけで削らない。
- 無生物主語を直すために行為者や実体験を作らない。確認済みの事実に伝聞を機械的に足さない。
- 記号や定型句は文脈で判断する。引用、必要な案内、正当なMarkdownを保つ。
- lintの出力は専用の一時ディレクトリへ保存し、既存の原稿やJSONを消さない。

## 研究から言える範囲

大西夢の卒業論文は、本調査で約500字の人間・AI各20篇を比較している。文長の散らばりなどの観察は参考になるが、各種SNS投稿や現在のモデルに共通する編集規則ではない。旧版は文長の**標準偏差**を各文の長さと取り違え、説明を強めすぎていた。

Zaitsu & Jin（2023）は日本語テキストの出自分類を調べた研究で、語句を削ったり文長を変えたりすると文章が良くなることを検証したものではない。

原論文へのリンク、確認したlintの状態、取り下げた推論は [証拠と適用範囲](ja-human-writing/references/evidence-ja.md) にまとめた。類義語、比喩、接続詞は、統計の方向へ合わせるために増減せず、意味と読みやすさで判断する。

## インストール

**前提**:[Claude Code](https://claude.com/claude-code) が動く環境。ターミナルを一度だけ使う。追加の課金は不要(Claude の利用枠の中で動く)。

ターミナルを開いて、この3行を上から順に貼る。

```bash
mkdir -p ~/.claude/skills
git clone https://github.com/vincent-wen789/ja-human-writing.git
cp -R ja-human-writing/ja-human-writing ~/.claude/skills/
```

機械チェッカーも入れるなら(任意・推奨)、続けてこの2行。

```bash
git clone https://github.com/coji/natural-japanese.git
cp -R natural-japanese/skills/natural-japanese ~/.claude/skills/
```

以降ターミナルは使わない。

- **機械チェッカーは任意。** natural-japanese を入れなければ、その工程が手動チェックリストに降格するだけで、スキル自体は動く

- **Windows** の場合、`cp -R` を PowerShell の `Copy-Item -Recurse` に読み替える

## 使う

Claude Code に依頼する。

```text
このnoteの下書きを軽く推敲して。事実と語気は変えず、AIっぽい空回りや重複がある箇所だけ直して。
```

変更理由も欲しければ、その旨を添える。新稿では「この素材からnote記事を書いて」と渡せる。素材が足りなければ、確認できる情報を調べたり、本人にしか分からない点を質問したりする。体験を作って埋めない。

ビジネス文書や技術文書は情報の整理を優先し、個人の語り口や句長の変化を強制しない。敬語チェックは必要に応じて使える。

## 自分の文体を参考にする

納得している過去原稿を1〜3本渡すと、語彙、判断の下し方、敬体の締め具合を参考にする。繰り返す語や有効な比喩も、書き手の声を担っていれば残す。統計上の「人間らしさ」へ揃えることはしない。

## 既存スキルとの関係

素材の確認と語りの位置は [human-writing](https://github.com/KKKKhazix/human-writing) をもとに日本語へ適応した。語彙表は stop-ai-slop-jp と slop-nuki と重なる。重ねて使う場合も、本スキルでは情報の保全と作者の声を個別ルールより優先する。

natural-japanese は任意の機械検査として呼ぶ。未導入でも手動確認で使える。`references/` は関連する判断が必要なときだけ読み込む。コンテキスト量はモデルや読み込むファイルによって変わるため、旧版のトークン概算は削除した。

## 限界と検証

- 主な対象は意見稿、個人の文章、SNS投稿。文書タイプを無視して同じ改稿をしない。
- 短文では統計が適用外になりやすい。指摘の有無から文章の自然さや出自を断定しない。
- [examples/](examples/) は旧版の作例とlint結果の記録。改稿効果の証明でも、現在の推奨手順でもない。
- 今回はルールの整合性と、内容を変えないための制約を見直した。独立した読者による盲検比較で、改稿品質の向上を実証したわけではない。
- 上流スキルの変更への追従は手動。問題や誤検知はIssueで知らせてほしい。
